# 前端迁移到 Vue 的工作量评估

评估基线：1.1.0（Django 6.1，服务端渲染 + 原生 JS）。本文只评估，不含实施。

## 一、现有前端真实体量

| 项目 | 数量 | 说明 |
| --- | --- | --- |
| 模板 | 80 个 / 3294 行 | 平均 41 行，最大 `inspections/profile_modal.html` 234 行 |
| 视图函数 | 123 个 | 全部函数视图，无类视图 |
| URL 路由 | 88 条 | |
| 页面（`render()`） | 32 个 | 其余 56 条路由返回 JSON、文件或重定向 |
| 已有 JSON 端点 | 12 个 | `JsonResponse`，AJAX 雏形 |
| 表单 | 15 个类 / 91 个字段 | Django Form 负责渲染与错误回显 |
| 模板逻辑 | 120 个 `{% for %}`、442 个 `{% if %}`、116 个 `{% url %}`、38 处 CSRF | |
| 自定义模板标签 | 10 个 | `custom_filters.py` 2 个、`extras.py` 8 个 |
| 前端 JS | 22 个 / 2703 行 | 最大 `table_workspace.js` 456 行 |
| CSS | 7 个 / 3112 行 | |
| 前端测试 | 108 个（`node --test`） | 纯逻辑测试，不依赖 DOM 框架 |

### 项目已经在用 Vue

这不是从零引入。网络拓扑页（`/operations/overview/`）整页是 Vue 3.5.43 应用：

| 组成 | 文件 | 行数 |
| --- | --- | --- |
| 根组件、视图缩放、链路筛选 | `static/app/js/operations-overview/app.js` | 244 |
| 拓扑归一化、可见性剪枝、布局 | `topology.js` | 244 |
| 30 秒轮询与手动刷新控制器 | `state.js` | 135 |
| 背景氛围效果（canvas） | `effects.js` | 73 |

落地方式已经固化，且是被写进架构决策的：`static/vendor/vue/` 存官方 ESM 浏览器构建（README 明确「运行页面不得从 CDN 加载 Vue」），模板用 `{{ snapshot|json_script:'operations-overview-bootstrap' }}` 注入首帧数据避免额外请求，挂载点 `#operations-overview-app` 带 `data-snapshot-url` 指向 `operations_overview_data` JSON 视图，`createApp({ delimiters: ['[[', ']]'] })` 避开 Django 的 `{{ }}`，`<noscript>` 兜底。`docs/changelog.md` 记录的口径是「Vue 仅用于运维总览页，其余为服务端模板 + 原生 JS」。

所以真正的问题不是「要不要上 Vue」，而是**这条边界要不要扩、扩到哪几页**。

结论先摆出来：**模板本身很小（3294 行），换成 Vue 的模板重写不是主要成本。真正的成本在把「服务端渲染 + 表单 POST + 重定向」改成「API + 单页应用」，这等于重写 123 个视图的契约，并重建一层现在由 Django 免费提供的能力。**

## 二、成本拆解

| 工作项 | 人日 | 依据 |
| --- | --- | --- |
| API 层（约 95 个端点） | 30–40 | 123 个视图去掉纯重定向与文件下载后约 95 个需要序列化契约；DRF 已在依赖里，`tests/system/test_application.py` 用了 `APIClient`，但业务端点尚未建 |
| 前端基座（构建、路由、状态、请求层、权限、主题） | 10–15 | 项目目前零前端构建链 |
| 32 个页面重写 | 40–50 | 表格工作区类 8 个、弹窗表单类 12 个、看板/详情类 12 个 |
| 交互细节迁移 | 10–15 | 弹窗草稿恢复、条件字段联动、表格列偏好、批量操作、巡检进度轮询、拓扑 SVG（`topology.js` 244 行） |
| 测试重建 | 10–15 | 108 个 JS 测试重写；E2E 目前没有，SPA 模式下必须补 |
| 部署链改造 | 5 | `deploy/setup.py`、`collectstatic`、CI 增加 Node 构建 |
| 双轨期回归 | 15–20 | 旧页面保留可用、逐页切换期间两套并存 |

合计 **120–160 人日**，单人 6–8 个月，两人并行 3–4 个月（含协作损耗）。

## 三、被低估的三块

**1. `table_registry.py` 是自研的配置驱动表格层。** 列显隐、筛选、排序、分页、批量选择、导出、偏好持久化全部由它驱动，模板只是一层壳。前端换成 Vue，这层能力要在组件里重建一遍，否则用户体验直接倒退。这是全项目最容易被漏算的一块。

**2. 表单即契约。** 91 个字段的校验规则、错误回显、联动显隐现在全在 Django Form 里免费获得。改 API 后，校验要么留在后端返回错误字典（前端再映射到字段），要么前后端各写一遍。15 个表单类里 `Network_Device` 一个就有 83 个模型字段。

**3. 认证与文件通道。** 现在是 session + CSRF + `login_required` 装饰器。SPA 要处理 CSRF 令牌获取、401 跳转、权限拒绝的页面级拦截。另有配置备份原文件、多设备 ZIP、CSV 导出、PC 采集脚本下载——这些走浏览器的下载通道，在 SPA 里要改成带鉴权的 blob 请求，`tests/devices/test_configuration_backup_views.py` 有三个用例专门锁这条链路。

## 四、三个选项

**A. 维持现状（推荐）**

不投入。理由不是"够用就行"，而是：换成 Vue 之后，功能集合不变、页面数量不变、后端仍然要写 95 个端点。投入 120–160 人日换来的净收益是"组件化"和"局部刷新"，而这两点在当前页面上并非主要痛点——`table_workspace.js` 已经用 fetch 做了局部刷新，108 个测试在跑。

同等时间投入 [proposal-1.2-roadmap.md](proposal-1.2-roadmap.md) 里的五项，能新增能力；投入迁移则原地踏步。

**B. 扩大既有边界：按页挂 Vue（若要提升交互，选这个）**

不是「引入 Vue」，是复制拓扑页那套已经跑通的模式：vendored ESM、`json_script` 注入、`delimiters` 改括号、无构建链、无部署改动。任何一页出问题，删掉 `page_scripts` 里那行 module 引用就退回原模板。

按交互密度排序，值得接管的页：巡检配置弹窗（`profile_modal.html` 234 行，条件字段最多）、设备采集设置（`collection_settings_body.html` 217 行）、告警策略弹窗（`policy_modal.html` 86 行 + 联动逻辑）、域控组成员（`group_members.html` 199 行）。

成本：每页 2–4 人日（模式已验证，比首次落地便宜），四页约 **10–16 人日**。拓扑页不动，它已经是 Vue。

**C. 全量重写（不建议）**

120–160 人日，期间功能冻结或双轨维护。除了"技术栈现代化"，没有一项用户可见的新能力。且必须一次性完成认证、文件通道、表格层、10 个模板标签的等价实现，否则中间态会长期无法上线。

## 五、如果非要全量，最小可行路径

1. 先建 API 契约层（DRF + 序列化器），旧模板改为消费同一套端点，页面行为不变——这一步就能独立验收，且让后续迁移不再依赖视图层改造。
2. 前端只做基座 + 一个域（如 `devices`），跑通登录、列表、详情、编辑、导出五条链路。
3. 按域推进，每域完整替换后再删旧模板，不做半成品并存。
4. 最后处理巡检进度这类依赖实时刷新的页面；拓扑页无需改动，它已是 Vue，迁移时只需把它接入新基座。

顺序颠倒（先写页面后补 API）会让每个页面都重写一次数据获取，这是这类迁移最常见的浪费。

## 六、结论

全量迁移 120–160 人日，约 6–8 个月单人，收益是架构现代化而非新功能。当前 3294 行模板、2703 行 JS 的规模，以及 `table_registry.py` + 108 个前端测试构成的既有体系，说明前端并未成为瓶颈。

若目标是"界面更像现代产品"，做 B 方案四个页面即可覆盖交互最重的场景，成本约为 C 的十分之一，且沿用拓扑页已经验证过的模式，不新增任何基础设施。

最后一条判断依据：项目已经用 696 行 Vue 证明了这套模式在这个项目里能跑——vendored ESM、无构建、Django 注入首帧、JSON 端点增量刷新。既然它只落在了一个页面，说明当初的选择是「按需」，而不是「迁移」。评估的结论应该尊重这个既定事实：继续按需。
