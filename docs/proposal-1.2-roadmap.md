# 对标 Nexora 的能力评估与 1.2 路线建议

调研对象：`libing28390-sketch/Release-netops`（产品名 Nexora，v1.0.11，2026-10-28 发布）。
评估基线：本项目 1.1.0（Django 6.1、59k 行 Python、66 个迁移、MariaDB/PostgreSQL 双后端）。
本文只给判断与落点，不含实现。

## 一、对方是什么形态

| 维度 | Nexora | 本项目 1.1.0 |
| --- | --- | --- |
| 后端 | FastAPI + APScheduler + WebSocket | Django 6.1 + 自建任务队列/Worker |
| 数据库 | PostgreSQL 18 + pgvector + pg_trgm | MariaDB / PostgreSQL（同一套迁移） |
| 前端 | React 19 + TS + Vite + Three.js + xterm.js | Django 模板 + 原生 JS |
| 指标存储 | VictoriaMetrics + vmagent + Grafana | 无独立 TSDB，指标落关系库 |
| 规模 | 5080 个文件（其中 `backend/vendor` 2745 个） | 约 1600 个文件，依赖 8 个直接库 |
| 定位 | 一体化平台：CMDB/IPAM/监控/PAM/工单/AI | 资产台账 + 设备巡检 + PC 日志分析，只读为主 |

它不是「比我们多几个功能」，而是产品路线不同：它把运维当作需要工单、审批、会话审计和写操作的组织流程；我们做的是采集与取证。**照抄会让本项目从 6 万行长到 20 万行，运维面从一个 Django 进程扩到 Nginx + PG + Redis + VM + Grafana + Guacamole 六件套。** 所以下面只取能嵌进现有架构、且用现有数据就能做的部分。

## 二、值得借鉴的部分（按投入产出排序）

### P0：数据已经在库里，只缺最后一层

**1. 配置版本对比与漂移检测**

对方做的是：配置备份、版本 Diff、全文搜索、漂移检测四件套。
我们的现状：`DeviceConfigurationBackup` 已按「每台设备每天首个成功版本、保留最近 10 个」存好原始配置，但**没有任何对比入口**，只能下载两个文件到本地用别的工具比。`net/devices` 下 grep `diff` 无实现。

落点：无需新表。新增 `net/devices/configuration/diff.py`（标准库 `difflib`）+ 详情页对比视图 + 「与上一版对比」按钮。漂移检测是同一个能力的定时化：日备份与前一版比较，差异行数超阈值则产生一次告警事件，复用现有 `AlertPolicy` 的 `execution.failure` 之外的独立事件类型。

工作量：小。风险：配置原文含凭据（`enable secret`、`snmp-server community`），差异视图必须脱敏，且不能把原文写进告警消息。现有 `net/infrastructure/` 已有脱敏工具可复用。

**2. 告警维护窗口抑制**

对方：维护期抑制，且明确「维护窗口不暂停链路采集」——抑制的是通知，不是采集。这个区分很重要。
我们的现状：`AlertState` 有状态机，`AlertPolicy` 有继承模式，但**没有维护窗口概念**，计划内变更期间告警照样发。

落点：新增 `MaintenanceWindow` 模型（作用域 + 起止 + 重复规则 + 说明），在 `net/alerts/routing.py` 投递前判断命中则标记 `suppressed` 而非丢弃，保留证据。跨午夜、跨月的窗口计算是这类功能的经典坑，对方 v1.0.10 专门修过，实现时直接用半开区间 + 本地时区，并补 4 个边界测试。

工作量：小到中。风险：时区。本项目 `net.W001` 未解决（MariaDB 时区表缺失），窗口判断必须走 Python 侧 `settings.TIME_ZONE`，不能用数据库 `Trunc*`。

**3. 全局采集并发预算**

对方：`NETWORK_SSH_GLOBAL_CONCURRENCY=20`、`NETWORK_SNMP_GLOBAL_CONCURRENCY=30`、`BACKUP_CONCURRENCY=10`，并进一步拆出「CMDB 采集专用 SSH 容量池」，理由是别让自动化和 CMDB 抢同一份 VTY 配额。
我们的现状：只有**按巡检配置**的 `concurrent_workers`，没有跨任务总量。两个巡检配置同时跑、或一个大配置配 32 并发，就会把交换机 VTY 打满，表现为大面积「登录失败」而不是「并发过高」，排查方向会被误导。

落点：`net/settings.py` 加三个上限，`net/inspections/` 在执行器拿到设备前用进程内信号量限流。工作量：小。风险：多进程部署时进程内信号量只是近似上限，需要按 worker 进程数折算，并在文档里写明这个天花板（按 Ponytail 惯例留 `ponytail:` 注释与升级路径：换 Redis 计数）。

**4. IP 定位：输入一个 IP，返回在哪台设备的哪个接口见过**

对方：NSOT 网络事实库 + NPA 智能路径诊断。这是它最有含金量的部分。
我们的现状：`net/devices/network/default_profiles.py` 已经把 `arp_table`、`mac_table`、`lldp_neighbors`、`routing_table` 设为交换机/路由器/AC/AP 的默认巡检项，四个厂商的命令也齐了。也就是说**证据每天都在采，只是没有查询入口**，采完就沉在记录里。

落点：不改采集。新增一个查询视图，聚合最近一次巡检的 ARP/MAC/LLDP 结果，按 IP、MAC、接口三个维度反查，返回「哪台设备、哪个接口、哪次巡检、什么时候」。这一步拿到 NPA 大约八成价值，成本只有它的一小部分：不做路径推演，只做证据定位。真要做多跳路径，才需要路由表 + 对端接口的图算法，那是 P2。

工作量：中（主要是结果解析与索引）。风险：ARP/MAC 是**被动观察**，不等于终端在线，界面上必须写清证据时间，不能给「在线」结论——对方在 v1.0.11 里专门强调过这一点。

### P1：需要新表，但结构简单

**5. 轻量 IP 台账（网段 + 地址登记 + 冲突提示）**

对方：Prefix、IP、地址池、VIP、DHCP 租约，外加六类对账（发现未登记、信息冲突、长期未发现、登记后未发现、归属待确认、来源不可用）。
我们的现状：完全没有 IP 维度，设备只有单个管理 IP。

判断：**六类对账不要抄**。它需要「完整采集代次」的概念（哪次巡检覆盖了哪个网段的全量）、观察历史累积、以及「采集不可用不等于核对通过」的三态判断，是一整套证据体系。我们做「网段台账 + IP 登记 + 与 ARP 观察对比出冲突/未登记两类」，能覆盖日常 90% 的用途，代码量约为对方的四分之一。

落点：`net/models/ipam.py` 三张表（`IPSubnet`、`IPAddress`、观察快照复用现有巡检结果），页面挂 `index/devices/` 下。与设备台账用 IP 弱关联，不建强外键——设备 IP 会变，强关联会产生大量孤儿行。

工作量：中。风险：容易滑向「做成 IPAM 产品」，需要在第一版就砍掉地址池与 DHCP 租约。

**6. 全局操作审计**

对方：全局审计日志 + 凭据轮换。
我们的现状：只有域控操作有审计字段（`net/models/domain.py` 的审计字段不可修改），设备增删改、模板修改、凭据查看都没有留痕。

落点：Django middleware + 一张 `OperationLog` 表，记录谁、什么时候、对哪个对象、做了什么、来源 IP。写操作钩子用 `post_save/post_delete` 信号或直接在视图层记录，前者更省事但拿不到请求上下文。

工作量：中。风险：数据量。一次 CSV 导入 500 台设备会产生 500 行，需要按批合并成一条「批量导入 500 台」而不是 500 条明细。凭据字段绝不能进日志。

**7. 巡检报表与容量趋势**

对方：容量趋势、巡检与运行报表导出。
我们的现状：`net/exports/` 有 CSV 导出，但没有跨时间的趋势视图，也没有周期性 PDF/Excel 报表。

落点：前端图表（现有原生 JS，需选一个轻量图表库，或直接用 SVG 手绘——鉴于项目至今零前端依赖，倾向后者）。工作量：中。风险：低价值高成本，容易做成「好看但没人看」。建议先确认是否真有人要看。

### P2：评估后再定

**8. 多跳路径诊断**：需要全量路由表 + 对端接口映射 + 图搜索，且结论准确率依赖拓扑完整度。当前拓扑只覆盖 LLDP/CDP 邻居，缺静态路由与 VRF 区分。建议等 IP 定位用满一年再考虑。

**9. 轻量变更单**：若团队确实需要「谁在什么时候改了什么配置、谁批的」，最小形态是配置备份版本 + 变更说明 + 审批人三列，不引入完整 ITSM（服务目录、SLA、初审终审、回滚）。对方那套是为多人运维团队设计的，我们的人数是变量。

**10. TextFSM 外置解析模板**：对方有 230 个模板文件。我们的解析是 Python 函数，带单位换算、阈值、缺项判定等业务语义——TextFSM 只解决「从回显里抠字段」，抠出来之后仍要业务处理。引入它等于多一层依赖和一份模板资产（要跟 230 个文件同步升级），收益集中在「快速接新厂商」。建议在真正遇到接不动的厂商时再评估。

## 三、不建议照搬

| 功能 | 为什么不 |
| --- | --- |
| SSH/Web PAM、会话录屏回放 | 需要 WebSocket 终端、对象存储、录像编码、一次性授权、危险命令拦截，工程量超过本项目现有全部功能之和；且录屏涉及存储生命周期与合规。我们要审计，做操作日志就够。 |
| RDP/VNC（Guacamole） | 引入一个 Java 服务作为协议代理，部署从单进程变多组件，与「Windows 一键部署」的交付方式冲突。 |
| 3D 机柜 | Three.js + 资产建模，纯展示价值。2D 机架图若有需求，用表格即可。 |
| AI 中心 / RAG 知识库 | pgvector + Embedding + Provider 网关 + Token 审计 + 安全网关，一套独立子系统。若真要做，先做「自然语言查询巡检结果」这一个场景，别做平台。 |
| Playbook / 写操作编排 | 本项目从设计上就是只读采集（`docs/device-inspection.md` 明确不执行 SNMP SET、不调用户/策略修改接口）。加写操作等于推翻现有安全立场，需要重新做权限、二次确认、回滚与演练。 |
| 多租户 `tenant_id` 兼容层 | 对方是历史包袱（README 明说单组织保留字段仅作兼容）。我们从一开始就不做多租户，不要预留。 |

## 四、工程实践层面可借鉴的三条

**依赖管理**：对方 `backend/vendor` 打包了 2745 个文件，这会锁死升级路径——想换 FastAPI 版本得先处理 vendor 副本。我们 8 个直接依赖 + `requirements.lock.txt` 是对的，继续保持，不要为了「离线部署方便」把 wheel 塞进仓库。

**默认关闭的开关文化**：对方的 `AI_ENABLED=0`、`EXTERNAL_AI_ENABLED=0`、`NETWORK_WRITE_ENABLED=0`、`PRODUCTION_CREDENTIALS_ALLOWED=0` 全部默认关闭，需要显式开启。这和我们的 `NET_SECURE_COOKIES` / `NET_SECURE_SSL_REDIRECT` / `NET_SECURE_HSTS_SECONDS` 是同一套思路，新增危险能力时照这个模式办：默认关、文档写清开启后果、开启后界面有可见标识。

**升级路径写进文档**：对方 README 用整段说明 PostgreSQL 17→18 不能复用数据卷、必须 pg_upgrade。我们的 MariaDB 主版本跨版本升级同样是数据目录不兼容，但 `deploy/README.md` 没有这一段。这是低成本、高价值的补充。

## 五、建议的 1.2 范围

全部落在现有架构内，不引入新服务、不引入新依赖（`difflib` 是标准库）：

| # | 功能 | 新表 | 迁移 | 页面 | 采集改动 | 规模 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 配置版本对比 + 漂移告警 | 否 | 0 | 详情页加视图 | 无 | 小 |
| 2 | 告警维护窗口抑制 | 是 | 0067 | 告警设置 | 无 | 小 |
| 3 | 全局采集并发预算 | 否 | 0 | 无（设置项） | 限流层 | 小 |
| 4 | IP 定位查询 | 否 | 0 | 新页面 | 无 | 中 |
| 5 | 轻量 IP 台账 | 是 | 0068 | 新页面 | 无 | 中 |

建议顺序：3 → 1 → 2 → 4 → 5。第 3 项最便宜且立刻降低现场故障率；第 1、2 项补齐「有数据但用不上」的短板；第 4 项在没有任何采集改动的前提下把已有 ARP/MAC 证据变成可查能力；第 5 项是唯一需要产品决策的一项，放最后。

## 六、需要你决定的三个点

1. **IP 台账要不要做**。这是本方案里唯一会显著扩大功能边界的一项（从「设备巡检」延伸到「地址管理」）。做，则 1.2 之后本项目会被拿来和 IPAM 产品比较；不做，IP 定位（第 4 项）仍然能回答「这个 IP 在哪」，只是没有登记与冲突提示。
2. **趋势图表的前端依赖**。项目至今零前端第三方库，纯原生 JS + Django 模板。加图表要么手写 SVG（无依赖、可维护、样式受控），要么引入一个 30KB 级图表库。我倾向 SVG 手绘，因为只有折线一种形态。
3. **配置对比的脱敏边界**。差异视图默认打码 `password`、`secret`、`community`、`key` 相关行，需要确认是否还要提供「查看原文」的二次确认入口——提供则审计压力上升，不提供则排障时要下载原文件。
